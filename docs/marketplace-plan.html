Your own Claude Code marketplace

Plan for github.com/ok2ju/ai-dev-toolkit · written 2026-07-28

1Goal

One git repository holds every skill, agent, command, and hook you write, and any project can install them with two commands. Other developers can install them as well, as soon as you make the repository public.

2The honest part first

A Claude Code marketplace is not a product, it is simply a git repository with one JSON manifest inside it. Claude Code clones the repository and reads that manifest, so there is no server, no build step, and nothing to upload.

The work here is therefore small, and the only genuine risk is the decision to make it large, so skip every item below:

  • A web catalog or a dashboard, because the /plugin command already lists everything you publish.
  • A monorepo toolchain such as Nx or Turborepo, because nothing inside this repository compiles.
  • One repository for each plugin, because every extra repository means another marketplace update to run.
  • A release pipeline that packages files, because pushing to git is already the release.

The second risk is choosing the wrong unit, because a marketplace lists plugins and nothing else. A bare skill or a lone agent cannot ship on its own, so each one must live inside a plugin. The plugin split is therefore the one design choice that really matters, because fixing it later needs renames, and renames break every installation.

You already install plugins from other marketplaces, so keep this layout close to theirs. A familiar shape removes the context switch, and moving a plugin between two marketplaces becomes a folder copy.

3Layout

ai-dev-toolkit/
├── .claude-plugin/
│   └── marketplace.json        # the whole registry, one file
├── plugins/
│   ├── core/                   # your daily drivers
│   │   ├── .claude-plugin/
│   │   │   └── plugin.json
│   │   ├── skills/
│   │   │   └── review-diff/SKILL.md
│   │   ├── agents/
│   │   │   └── scout.md
│   │   ├── commands/
│   │   │   └── ship.md
│   │   ├── hooks/hooks.json    # only when hooks are needed
│   │   ├── scripts/            # hook scripts live here
│   │   ├── .mcp.json           # only when the plugin owns an MCP server
│   │   └── README.md
│   └── frontend/               # same shape, different domain
├── scripts/
│   └── validate.mjs            # one file, no dependencies
├── .github/workflows/ci.yml
├── docs/
└── README.md

Every plugin repeats that same shape, and every folder is optional except .claude-plugin/plugin.json, so that single rule is the whole convention.

4The two manifests

Root: .claude-plugin/marketplace.json

{
  "$schema": "https://anthropic.com/claude-code/marketplace.schema.json",
  "name": "ai-dev-toolkit",
  "description": "Personal Claude Code plugins: skills, agents, commands, hooks.",
  "owner": { "name": "ok2ju", "email": "soulSpringg@gmail.com" },
  "metadata": { "version": "0.1.0", "pluginRoot": "./" },
  "plugins": [
    {
      "name": "core",
      "source": "./plugins/core",
      "description": "Daily drivers: diff review, ship flow, scout agent.",
      "version": "0.1.0",
      "category": "development",
      "keywords": ["review", "git", "workflow"]
    }
  ]
}

Per plugin: plugins/core/.claude-plugin/plugin.json

{
  "name": "core",
  "description": "Daily drivers: diff review, ship flow, scout agent.",
  "version": "0.1.0",
  "author": { "name": "ok2ju" },
  "hooks": {
    "SessionStart": [
      { "hooks": [ {
          "type": "command",
          "command": "node \"${CLAUDE_PLUGIN_ROOT}/scripts/on-start.mjs\"",
          "timeout": 5
      } ] }
    ]
  }
}

Two rules that bite. Hook commands must always use ${CLAUDE_PLUGIN_ROOT}, because a relative path breaks as soon as Claude starts from another folder. The version must also match in both manifests, and because nothing checks that for you, the validator will.

5How to split plugins

Split plugins by the job they perform, never by file type. A skills plugin next to an agents plugin is the wrong cut, because nobody wants half a workflow.

PluginHoldsWhy it deserves its own unit
coreHabits you want in every repoAlways installed first.
frontendReact, CSS, and Figma workDead weight in a backend repo.
infraTerraform, CI, deploysWide blast radius, so opt-in.

Start with core alone. Add a second plugin only once a skill really stops fitting inside core. Three solid plugins are easier to live with than ten fragments, because every installation stays a manual step.

Plugin names are your public interface, so pick short lowercase names separated by dashes. A later rename breaks every installation, and only a renames map in the root manifest can rescue it. Check the official marketplace first, otherwise two entries in one list will collide over a single name.

6Versions

  • Bump the plugin version on any change, and bump the marketplace version whenever a plugin is added or dropped.
  • Use patch for wording, minor for new files, and major for a rename or a deleted command.
  • Skip git tags and changelogs at first, and add a CHANGELOG.md to a plugin only once someone besides you depends on it.

7The one script you need

Write scripts/validate.mjs in plain Node with no extra packages, and make it fail loudly on the problems below:

  1. Bad JSON in either manifest, or a source path that points at no folder.
  2. A plugin folder missing from marketplace.json, which is the mistake you will make most often.
  3. Two plugins that share one name, or a version that differs between the root manifest and the plugin manifest.
  4. A SKILL.md or agent file whose frontmatter lacks name or description, because Claude Code silently ignores those files.
  5. A hook command written without ${CLAUDE_PLUGIN_ROOT}, which breaks the moment somebody installs the plugin elsewhere.

Run that script from .github/workflows/ci.yml on every push, and the pipeline is complete. Some 120 lines of validation catch nearly every mistake you realistically make.

8Daily loop

# once, point Claude at your local checkout
/plugin marketplace add ~/Projects/ai-dev-toolkit
/plugin install core@ai-dev-toolkit

# edit files, then reload
/plugin marketplace update ai-dev-toolkit

# once published, on any other machine
/plugin marketplace add ok2ju/ai-dev-toolkit

Point Claude at the local checkout while you build. That tests the genuine installation path, instead of a copy inside ~/.claude. Restart the session after any hook change, since hooks load only at session start.

Leave autoUpdate disabled on your own marketplace. You want to break your configuration deliberately, rather than in the middle of a task.

9Real risks

  • Hooks execute code on your machine, which holds for your own plugins and for anything you add from a stranger. Read the hook scripts beforehand, because this is the only genuine security boundary here.
  • A public repository leaks private knowledge, because skills carry client names, internal URLs, and ticket workflows. Start private, then open up one plugin at a time.
  • Token bloat is real, because every skill description loads into every session. Long descriptions cost money and attention, so each one belongs in a line or two.
  • Cross-plugin imports do not exist, so a skill in frontend cannot reuse one in core, which leaves two options: copy a few lines, or keep the shared material in core and treat core as a prerequisite. Building an import layer is never worth it.
  • Nothing checks behaviour, because the validator inspects structure rather than results. Only real usage reveals whether a skill works, so that gap is worth accepting.

10Build order

StepWorkFinished when
1Root marketplace.json, plugins/core with one real skill, README/plugin install core@ai-dev-toolkit works from the local path
2Move your three best skills and agents into coreYou lean on them in a live task
3validate.mjs plus CIA broken commit fails the build
4Push to GitHub, install on a second machineInstall works from the repo name
5Split out a second plugin, only if core got crowdedBoth plugins install clean

Step one takes under an hour, steps two through four deliver the actual value, and step five may never arrive, which would be a healthy outcome.

Adding a plugin should mean one new folder plus one new manifest entry. Whenever it demands more than that, the setup has grown a layer it never earned.
